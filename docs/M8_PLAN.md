# 모델 관리 대시보드의 남은 계획 — M8부터

기준일: 2026-10-17 · M8 구현·검증·저장소 반영 승인 / 확인 환경의 핵심 구현·실검증 완료 / 소스·문서 반영 범위

## 완료 범위를 바로잡기

M0–M6는 문서로 승인한 **TTS 중심 1차 범위**를 완료했고 M7에서 독립 Windows 앱과 후속 새 두 모델 실행·재생·저장을 검증했다. 이는 원구상 화면의 다종 모델 등록·통합 상태·모든 실행 어댑터를 모두 완성했다는 뜻이 아니다. 기존 [출시 이력](M7_REPORT.md)과 [새 A/B 결과](M7_AB_REPORT.md)는 그대로 보존한다.

현재 목록의 파일/폴더 후보와 실제 등록 모델은 다르다. 이미지의 예시 숫자를 초기 데이터로 넣거나 폴더 수를 등록 모델 수로 바꾸지 않는다. 범위별 기능과 실제 증거로 진척을 판단하며 가중치 없는 단일 구현률을 제시하지 않는다.

## 단계별 로드맵

| 단계 | 남은 기능 | 완료 게이트 | 현재 범위·상태 |
|---|---|---|---|
| **M8 모델 등록·통합 상태** | 안정적인 모델 ID, 등록/편집/보관, 모델별 메타데이터·관찰/검증 구분, 등록/실행 검증/구성 확인 필요 KPI | 새 등록·편집·보관·재시작·목록/상세/KPI 정합, 오류/빈 상태·키보드·대표 폭, 현재 모델 자산과 새 실제 실행 연결 | 확인 환경의 핵심 실제 검증 완료. 미검증 경로·화면 범위는 보고서에 별도 명시 |
| **M9 통합 작업 기록·설정·차트** | 수집/준비/실행/비교 기록을 공통 시간축과 필터로 조회, 설정 위치/적용 범위 명시, 같은 조건 측정값의 시간·메모리 차트 | 원래 run/scan/prep로 추적·과거/현재 구분·미수집 값 처리·필터/상세·재시작, 숫자/그래프 단위·비교 조건·접근성 검증 | 후보 3 확인 환경에서 기록/설정/차트·새 A/B·재생/저장·재시작 검증 완료. 소스/문서 반영 범위. [M9 계획](M9_PLAN.md)·[진행 보고](M9_REPORT.md) |
| **M10 다종 모델 실행** | Whisper STT, 이미지 생성, Llama LLM, TAPIR 추적을 각각 별도 어댑터로 추가 | 지정 원본 존재·라이선스·revision/해시·환경·입력/출력 계약 확인 후 어댑터별 새 실제 E2E·오류·취소·저장 검증 | 어댑터별 세부 범위와 실행 조건을 먼저 확정. 이번 실행 범위 아님 |

M10은 하나의 “범용 실행” 버튼으로 완료 처리하지 않는다. Whisper는 새 음성 입력과 전사, 이미지는 새 프롬프트와 생성 이미지, Llama는 새 텍스트와 응답, TAPIR는 지정 새 영상/점과 추적 출력을 각각 검증해야 한다. 목록에 이름이 보이는 것과 해당 실행 지원은 별개다.

## M8 모델 단위와 편집 계약

- **안정적인 모델 ID**: 등록 때 UUID를 생성하고 이름·폴더명·재수집 scan ID가 달라져도 같은 등록 항목의 ID는 유지한다. 관찰된 폴더를 자동으로 모델로 등록하지 않는다. 편집은 row version을 비교하는 CAS 방식으로 오래된 화면의 저장 충돌을 검출한다.
- **사용자 정보**: 표시 이름·설명·용도·사용자 버전 이름·태그·메모를 관리한다. 이 정보는 사용자가 붙인 설명이며 사실 검증을 대신하지 않는다.
- **실제 자산 정보**: 계정/허용 폴더/파일 구성의 참조와 관찰 출처, 필요한 경우 공식 artifact revision·고정 manifest·파일 해시를 별도로 기록한다. 사용자 버전 이름과 실제 가중치 revision을 혼동하지 않는다.
- **관찰 출처**: 수집 기록과 당시 파일 메타데이터를 연결한다. 해당 파일의 존재·해시·환경·추론을 모두 검증했다는 뜻은 아니다. 변경되거나 찾을 수 없는 참조는 숨기지 않는다.
- **보관**: 기본 제거 동작은 등록 항목을 보관 처리한다. 원본 모델·Drive 파일·기존 실행·WAV·개인 DB를 삭제하거나 이동하지 않는다. 보관 항목의 노출과 KPI 포함 여부를 명시한다.
- **기본값**: 새 registry는 비어 있다. 가짜 예시 모델·역사적 PASS를 넣거나 과거 성공 기록을 자동으로 새 등록의 현재 검증으로 승격하지 않는다.

등록 모델을 다루는 **모델 관리** 화면을 기본 화면으로 두고 기존 **파일 후보 탐색**은 별도 관찰 경로로 보존한다. 등록 모델을 선택한 실행은 registry 전용 API를 통해 고정 adapter·manifest·artifact fingerprint와 연결한다. 과거 결과의 model_id만 맞는다는 이유로 성공 상태를 자동 연결하지 않는다.

지원 고정 adapter의 로컬 원본 폴더를 명시하면 manifest 구성 파일의 전량 크기·SHA-256을 등록·명시 변경 시 확인한다. 빈 폴더·Drive 메타데이터 관찰만으로 구성 확인을 통과시키지 않는다. 실행 직전에는 등록 원본과 현재 준비된 모델 구성의 내용 해시를 다시 대조한다. 자동 화면 조회의 기록·stat 확인을 매번 전량 내용 해시 검증으로 표현하지 않으며 최근 검증 시각·구성·환경의 한계를 표시한다.

### 두 DB의 보존·복구 경계

기존 `inventory.sqlite3`의 scans/files exact schema와 정상 backup/restore 계약은 유지한다. 현재 구현은 별도 `registry.sqlite3`의 models·model_references를 사용하고 스키마 버전은 PRAGMA user_version으로 확인한다. artifact는 모델 row의 JSON·generation·fingerprint와 같은 트랜잭션에서 저장한다. 새 실행 연결은 별도 DB 쓰기 대신 run state와 provenance의 고정 registry_binding으로 기록해 교차 쓰기 중 불완전 연결을 줄인다. 고정 소스·새 패키지·실제 설치본을 대조했으며 기존 개인 DB를 제자리 실험 대상으로 삼지 않았다.

기존 inventory 복구는 registry 등록·편집·보관·실행 연결을 자동 복원하지 않는다. registry의 초기화·버전 검사·트랜잭션·재시작 보존을 별도로 검증했다. 현 버전은 registry 통합 backup/restore를 제공하지 않으며 이는 후속 계획이다. 두 DB가 함께 자동 snapshot/원자 복원된다고 주장하지 않는다. 어느 DB의 복구도 인증·모델 원본·runtime·WAV 전체 복구나 손상 원본 수리를 뜻하지 않는다.

## 상태와 상단 세 숫자

관찰·구성·파일 무결성·런타임·실제 실행을 각각 출처/시각과 함께 관리한다. 등록했다는 사실만으로 실행 검증 상태를 주지 않는다. 지원하지 않는 실행 유형은 “미지원”, 확인하지 않은 항목은 “미확인”으로 표현하고 실패와 구분한다.

| KPI | 계산 원칙 |
|---|---|
| **등록 모델 수** | 보관되지 않은 active UUID 수. 파일 수·관찰 폴더 수와 별도 |
| **실행 검증 모델 수** | current artifact_generation·fingerprint에 registry 전용 API로 명시 연결한 새 run이 succeeded인 active 모델 수. 중복 run 수를 더하지 않음 |
| **구성 확인 필요 모델 수** | 구성이 unknown 또는 incomplete인 active 모델 수. 미확인·명시 부족·참조 접근 범위 불일치를 사유로 구분한다. 실행 실패 횟수나 파일 실패 개수를 더하지 않음 |

새 빈 등록은 실행 미검증·구성 미확인으로 시작해 구성 확인 필요에 포함한다. 실행 실패는 별도 상태로 표시하며 구성 미확인과 섞지 않는다. 메타데이터(표시 이름·설명·사용자 version label·태그·메모) 편집은 증거를 유지한다. references·adapter·실제 artifact revision 변경은 generation을 바꾸고 현재 검증 연결을 해제한다. 보관·보관 해제도 generation을 바꾸므로 보관을 되돌렸다는 이유로 과거 성공을 현재 PASS로 복원하지 않는다. 이전 결과는 과거 증거로 보존하며 새 generation의 검증 성공으로 승격하지 않는다. 이 상태 집합과 KPI를 API·화면에서 동일하게 계산하고 경계 테스트로 확인한다.

## M8 검증과 완료 판정

1. 새 고유 검증 경로에서 empty registry·모델 등록·중복/잘못된 입력·편집·보관·재시작과 기존 inventory 보존을 확인한다.
2. 모델 목록/상세/세 KPI의 계산 단위·상태를 같은 데이터로 대조한다. 미지원/미확인/실패/과거 성공·오래된 관찰·참조 변경·보관 항목이 섞여도 잘못된 PASS가 생기지 않아야 한다.
3. 지정 TTS 자산을 새 등록에 명시 연결하고 현재 자산 해시와 **새 입력의 실제 실행**을 연결한다. 이전 WAV·실측·테스트 결과를 이번 연결 검증으로 대체하지 않는다. 실제 실행 전 모델 단위 검증 완료를 선언하지 않는다.
4. 새 실제 화면에서 빈 목록·등록/편집/보관·상태 필터·상세·오류·키보드/포커스·대표 화면 폭을 검증한다. 목업이나 API 통과만으로 실제 사용 흐름을 대신하지 않는다.
5. **M8 변경을 포함해 새로 빌드한 패키지·새 검증 설치본·현재 소스·새 실행**을 독립 검토와 연결하고 제한을 기록한다. 기존 0.7.1의 테스트·패키지·GPU/WAV 성공으로 M8 검증을 대체하지 않는다. 공개 파일 목록·개인정보 검토·고정 커밋 원문/비변경 보존 검증 후 저장소에 반영한다. 이후 사용자 가이드를 실제 화면에 맞춘다.

후보 3의 패키지·실제 설명 편집 수리·보관/해제·검색·새 0.6B 연결 실행·재생/저장을 확인했다. 새 성공 후 편집의 검증 유지와 정상 재시작의 상태·파일 보존도 확인했다. 계획된 전체 폭·실제 Drive 후보 경로 등은 미검증이다. 소스와 비식별 문서를 함께 반영하며 프로그램 공개 Release와 구분한다. 한계와 게이트 상태는 [M8 보고서](M8_REPORT.md)를 따른다. 수정판 증거와 게시 결과가 도착하면 각각 갱신하며 기존 성공으로 수정판을 자동 통과시키지 않는다. 기존 릴리스·코드·모델 원본·인증·개인 DB·출력은 보존한다.

## 이 구상의 필수로 추가하지 않는 것

Drive 쓰기·모델 원본 업로드/삭제·스토리지 정리·원격 GPU는 첨부 화면의 필수 기능으로 간주하지 않는다. 이번 M8은 파일 삭제·업로드 없이 등록 정보를 로컬에서 관리한다. **관리 에이전트와 일정 실행 등 자동화는 향후 자동화 선택 범위**로 남긴다. 관리 자동화의 중요도를 낮추는 의미가 아니며, 실제 행동·권한·확인/취소·실패 복구의 범위를 정해 승인받기 전 실행하지 않는다. 기존 브라우저/OS 보안 설정을 변경하지 않는다.
